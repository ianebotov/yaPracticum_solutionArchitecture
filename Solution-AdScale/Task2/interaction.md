Схема взаимодействия(AdScale)

Выбор протоколов

Внутреннее взаимодействие
API Gateway - Bidding Service: gRPC т.к. это критичный путь с требованием к SLA < 100 мс. Требуется высокая пропускная способность с низой задержкой
Bidding Service - Campaign Service: gRPC т.к. это внутренний вызов и задержка критична
Dashboard - Campaign/Financial/Analytics: REST т.к. задерзки не критичны, а реализация проста
Bidding Service - Statistics Service: Kafka т.к. синхронное получение не требуется, но важна гарантия доставик


gRPC для Bidding и Campaign, причины выбора
Задержка (latency)* = Низкая (работа с бинарным форматом)
Пропускная способность = Высокая
Внутренние вызовы между сервисами = Отлично

Kafka для событий, причины выбора
Producer не зависит от consumer, события не теряются
Kafka обрабатывает миллионы сообщени в сек
Возможность перечитать данные при ошибках
каждый consumer может читать в своём темпе и не влияет на другие сервисы

Почему REST для Dashboard
Критерий	REST	gRPC	GraphQL
Формат данных =	JSON, читать легко
Задержка (latency)* = Средняя
Пропускная способность = Средняя
Поддержка браузера = Нативная


Внешний протокол: интеграция с DSP
Не меняем поскольку есть уже подключенные DSP и изменение контракта критично
