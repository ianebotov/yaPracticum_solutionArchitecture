AS-IS анализ архитектуры AdScale
Обзор текущей системы

AdScale — SaaS-платформа для размещения цифровой рекламы. Текущая реализация — гибридный монолит на C++/Go/Python/Node.js, работающий на единственном инстансе PostgreSQL, без кеша, очередей и контейнеризации. Деплой — вручную, инфраструктура — один production-кластер.

Компоненты:
Ad Server - C++, Go. Приём HTTP-запросов, идентификация пользователя, подбор кандидатов
Auction Engine - C++. Взвешивание ставок, бизнес-правила, расчёт победителя
Delivery Service - Node.js. Формирование HTML/JS-разметки баннера и HTTP-ответа
Statistics Service - Python. Запись кликов и показов
Financial Service - Go. Списание средств, счета, балансы
Analytics Service - Python. SQL-аналитика по БД
Advertiser Dashboard - Node.js, JS. Web UI: управление кампаниями, отчётность

Внешние системы:
DSP-партнёры
Платёжный шлюз (пополнение бюджетов)

Узкие места:
Уже запросы отрабатывают за 110–120 мс при требовании ≤ 100 мс, любое увеличение трафика (+20% через 3 месяца, 18000 RPS) гарантированно усугубит деградацию
Auction Engine — критический модуль зависящий от PostgreSQL
Statistics Service - синхронная запись каждого клика/показа в PostgreSQL
Analytics Service — формирует тяжёлые запросы напрямую в PostgreSQL что может «положить» всю систему.
!Все модули взаимодействуют с PostgreSQL, он имеет один инстанс. Это приводит конкуренции (ставки, финансы, события и аналитика борются за ресурсы).

Точки отказа:
PostgreSQL  - Полный простой платформы, Высокий приоритет
Это монолит - Падение одного компонента приводит к простою всего, Высокий приоритет
Отсутствие кеша - Деградация при росте нагрузки на чтение, Высокий приоритет
Ручной деплой - Человеческий фактор, долгий откат при сбое, Средний приоритет
Один кластер - Нет возможности масштабирования/миграции, Высокий приоритет

Проблемы
Монолит - все компоненты деплоятся вместе, невозможно независимо масштабировать один из...
Единая БД - все модули в одной PostgreSQL, высокая нагрузка действует на всех
Отсутствие асинхронных обменов - запись событий всегда синхронная, блокировки из за отсутствия разделения
Нет кеша - каждое обращение к данным идёт в БД
Гибридный стек языков - C++/Go/Python/Node усложняет реализацию
Нет контейнеризации - ручной деплой, нет горизонтального масштабирования

Риски
Превышение SLA ведет к штрафу - Финансовые потери, репутация. Нужен кеш, асинхронность
Сбои в работе ведут к проигрыш на аукционах, требуется защита от сбоев
Сбои платежного шлюза ведут к проигрышу аукционов, требуется защита от сбоя
Потеря клиентов при простое, требуется поэтапная миграция без простоя
Невозможность быстро подключить нового партнера, требуется интеграционный слой(API Gateway)

Итог
Текущая архитектура уже не поддерживает SLA и несоответствует цели(+20% трафика без деградации SLA через 3 месяца). Необходима модернизация с выделением критичных сервисов, введением кеша и очередей, разделением БД, контейнеризацией.
Полная перепись невозможна из-за бюджета и срока, требуется постепенная миграция
