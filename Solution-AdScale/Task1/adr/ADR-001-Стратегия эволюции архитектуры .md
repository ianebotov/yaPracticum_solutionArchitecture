ADR-001: Стратегия эволюции архитектуры (от монолита к микросервисам)

AdScale — монолитная SaaS-платформа (C++/Go/Python/Node.js) с единым PostgreSQL, работающая на пределе: 15 000 RPS, P95 = 110–120 мс при SLA ≤ 100 мс. Необходимо:
Подключить новую DSP-площадку через 3 месяца (+20% трафика и 18 000 RPS)
Обеспечить P95 ≤ 100 мс без деградации
В перспективе года — 50 000 RPS, микросервисная архитектура, SLA 99.9%

Ограничения
бюджет ограничен
срок 3 месяца до подключения первого партнера
требуется поддержать непрерывность бизнеса
полная перепись решения невозможна

Выбор варианта:
Оставить монолит + провести оптимизацию
Плюсы 
минимальные затраты, быстрый срок
Минусы
Невозможно независимо масштабировать Auction Engine и Statistics Service, при +20% RPS нужно масштабировать всё, а не только критичное
Единая БД уже приводит к конкуренции, выдержать SLA в ≤ 100 мс проблематично
Ручной деплой всего монолита это риск простоя при каждом релизе
Гибридный стек (C++/Go/Python/Node) приводит к сложности поддержки
Отсутствие защиты от сбоев приводит к отказову всего, падение аналитики роняет и аукцион
Вывод
монолит не может обеспечить P95 ≤ 100 мс при 18 000 RPS и 99.9% доступности. 

Сразу перейти на микросервисы
Плюсы
чистая архитектура с нуля
Минусы
Срок 3 месяца до подключения партнера не позволяет переписать сразу всё
Бюджет ограничен и не позволит переписать сразу все
Необходимо обеспечить непрерывность бизнеса
Команда 35 человек без несправится с паралельной разработкой всех требуемых сервисов
Все зависимости неизвестны и есть риск не учесть текущие особенности реализации
Вывод
полная декомпозиция сразу невозможна за требуемый срок и не укладывается в бюджет, так же несет риски простоя и возможность не учесть особености текущей реализации что критичо

Поэтапный переход с модульным монолит, на переходный период
Плюсы
Позволяет реализовать сервисы поэтапно и независемо, если новый сервис работает нестабильно можно вернутся в монолит и устранить проблемы без простоя
Позволяет поддержать увеличение нагрузки поэтапно, через 3 месяца до 18000 RPS и до 50000 через год
Минусы
В переходный период требуется поддержка и монолита и сервисов
нужен API Gateway для маршрутизации
Вывод
Реализация новых сервисов вокруг монолита с последующем перенаправлением трафика закрывает имеющиеся потребности. Данное решение выбрано в качестве целевого

Решение
Постепенная миграция монолитной системы на новую архитектуру 
Первая очередб - 3 месяца
1. Ввести API Gateway + Redis cache
2. Вынести Bidding Service в отдельный сервис
3. Добавить Kafka для передачи событий (клики, показы, события ставок)
4. Вынести Campaign Service, Statistics Service
Вторая очередь - 1 год
5. Вынести Analytics реализовав на read replica, Financial HA
6. Вынести остальные сервисы

Каждый сервис выделяется независимо, с собственной БД. Монолит постепенно замещается новыми сервисами.

Результат
Плюсы
Отсутствие простоя при миграции
Инкрементальная стоимость, оплата разработки за отдельные решения
Bidding Service масштабируется независимо
Event-driven обработка событий разгружает БД
В период миграции каждый сервис может быть обкатан независимо

Отрицательные
Временное сосуществование монолита и микросервисов увеличивает сложность эксплуатации
В переходный период данные дублируются
