Кеширование (AdScale)

Во время аукциона, нужно быстро узнать текущие ставки рекламодателей. Если каждый раз лезть в основную базу данных, это долго и возникает риск что БД не справится с нагрузкой. Поэтому решено использовать кеш, где будут хранится самые нужные данные. Сначала система смотрит в кеш, и только если там нет нужной информации идёт в базу.

В качестве кеша используется Redis, он работает отдельно от сервисов и хранит данные к которым обращаются чаще всего. Получение данных из Redis происходит быстрее, чем из PostgreSQL, и при этом PostgreSQL не нагружается

Кешируемые данные:
Ставки кампаний - критично, без этого аукцион не будет проведен
Список активных кампаний - актуальный список компаний продающих рекламу
Информацию о баннерах - размеры, форматы, картинки

Поддержание актуальности данных:
Удаление по TTL - Время, после которого данные автоматически удаляются поскольку считаются неактуальными. Следующий запрос пойдёт в базу и принесёт свежие данные.
Удаление по событю - Когда происходит изменение данных, например компании, сервис отправляет сообытие по которому данные удаляются из redis.
Прогрев кеша - При перезагрузке redis, система партиционировано загружает в кеш все активные кампании. Это позволяет получать данные из redis, не запрашивая их в БД после перезагрузки.

Добавление redis как кеша позволяет системе отвечать быстро, даже при большой нагрузке. Разные способы обновления данных гарантируют, что в кеше данные актуальны на момент запроса.

Отказоустойчевость
у Redis есть три основных сервера и у каждого есть своя запасная копия на другом сервере. Если один основной сервер падает, его копия становится основной, клиенты автоматически переключаются на него.
Если Redis полностью недоступен, сервисы начинают получать данные из PostgreSQL что приводит к деградации но исключает полную недоступность системы.
