Стратегия данных (AdScale)

AdScale работает с данными:
Транзакционные данные требующие согласованности(кампании, ставки, финансы, креативы), хранение в PostgreSQL
Аналитические данные для пользователей, для потока преобладает чтение(Клики, показы, конверсии), хранение в PostgreSQL read replica 
События, идет постоянным потоком но не требуют синхронной обработки (События по ставкам, события по кампаниям, финансовые события), хранение в Kafka

Для целевой архитектуры, микросерисы, требуется распределение данных по отдельным БД. Это позволит обеспечить:
Изоляцию сервисов: отказ одного сервиса не влияет на другие
Независимое масштабирование: можно масштабировать БД отдельно от сервиса
Чёткие границы: данные принадлежат одному сервису
Разные технологии: можно выбрать оптимальную БД для каждого типа данных

Распределение данных

| Сервис | БД |
| Bidding Service | bidding DB, PostgreSQL + Redis как кеш |
| Campaign Service | campaign DB, PostgreSQL |
| Analytics Service | PostgreSQL Read Replica |
| Statistics Service | statistics DB, PostgreSQL |
| Financial Service | financial DB, PostgreSQL |
| Delivery Service | delivery DB, PostgreSQL |


Обоснование
Read Replicas для Analytics Service
Analytics Service выполняет тяжёлые SQL-запросы что вызывает рост нагрузки и блокировки. Для исключения нагрузки на PostgreSQL необходимо реализовать PostgreSQL Read Replica поскольку незначительные задержки при репликации допустимы и сервис работает только на чтение

PostgreSQL для Statistics Service
Statistics Service обрабатывает поток событий, получаемый через kafka. Поток на запись и чтение сопостовим и требуется поддержать обе операции. 

PostgreSQL + Redis для Bidding Service
для Bidding Service критично получение данных о компаниях, при этом он так же отдает данные о результатах аукциона. Для снижения нагрузки на ББ смежных сервисов, реализуется Redis - кеш  

Миграция данных
Первоночально reads должен получать данные из БД монолита
При выделении сервиса из монолита данные нужно мигрировать :
Схемы в новые БД
Данные из БД монолита в новые БД. Поскольку в перехоный период данные фактически храняться в 2-х БД, требуется поддержать запись и в старую, и в новую БД с сверкой и устранением расхождений
После завершения перехода, требуется переключить reads на новую БД и остановить дублирование данных

Отказоустойчевость PostgreSQL
Для обеспечения отказоустойчивости требуется реализовать реплицирование master-slave
master - принимает все изменения данных. 
slave - постоянно получают копии данных с master.

При выходе из строя master:
Система фиксирует проблему и переключается на slave, делаяя ее главной. 
После востановления первого узла, он начинает работать как slave
